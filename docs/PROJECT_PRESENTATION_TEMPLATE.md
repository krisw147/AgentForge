# AgentForge 项目讲解模板

这份模板用于面试、作品集分享和技术复盘。先讲业务问题，再讲设计取舍，最后用
可观察结果证明实现，不要从技术栈清单开始。

## 1. 30 秒电梯陈述

> 我做了一个可自托管的 Agent Runtime 与 AgentOps 平台 AgentForge。它不只完成
> 一次模型对话，而是把 Agent 运行拆成可持久化的任务：独立 Worker 执行，工具调用
> 和 Trace 写入数据库，敏感操作经过人工审批后从检查点恢复，新版本通过准确率、
> P95 延迟和成本门禁后才能发布。项目同时支持 stdio 与 Streamable HTTP MCP，
> 并实现了多租户 Session 和 RBAC。

可替换字段：

- 目标岗位：`[AI 应用开发 / Agent 平台 / LLMOps / 后端]`
- 本人负责：`[独立设计并实现 / 负责 Runtime 与评测 / 负责平台工程]`
- 最有价值的成果：`[持久化执行 / MCP / 权限与审批 / 评测门禁]`

## 2. 两分钟主版本

### 0:00-0:15 一句话定位

讲解句式：

> AgentForge 是一个面向企业 Agent 的控制平面。我想解决的不是“模型怎么回答”，
> 而是“ Agent 运行失败、调用敏感工具或发布新版本时，平台如何保证可控和可追溯”。

要点：

- 明确这是平台项目，不是聊天机器人。
- 明确用户和业务场景：企业客服、退款运营、工具调用。

### 0:15-0:35 问题与设计目标

> 普通 Demo 通常在 HTTP 请求里直接调用模型和工具。这种做法有三个问题：Worker
> 崩溃会丢任务；退款等写操作没有人工控制；Prompt 或模型升级后无法证明质量没有
> 退化。因此我设定了四个目标：持久化执行、人工控制、完整 Trace、发布安全。

设计目标：

1. Durable execution：任务不因进程退出而丢失。
2. Human control：敏感工具必须审批。
3. Traceability：每个决策与工具结果可回放。
4. Release safety：版本发布必须经过回归门禁。

### 0:35-1:05 架构与执行链路

> 前端是 Next.js 控制台，API 使用 FastAPI。API 创建 Run 后只写入数据库并返回
> 202，不等待模型执行。独立 Worker 通过条件更新原子领取任务，记录租约、心跳和
> 尝试次数。每次模型、检索或工具步骤都先持久化事件，再进入下一步；浏览器通过
> SSE 看到实时快照。

建议顺序：

```text
Request -> API -> Run(queued) -> Worker -> Trace -> SSE
                              |
                              +-> Tool Gateway -> MCP / Mock API
```

关键数字：

- Worker 租约：12 秒
- 正常心跳间隔：约 4 秒
- 运行创建响应：HTTP 202
- MCP Bridge 默认单次调用超时：12 秒
- MCP 空闲会话回收：5 分钟

### 1:05-1:35 最值得讲的难点

从以下四项中选一项深入，不要全部平铺：

- **故障恢复**：租约过期后，任务回到队列，新 Worker 增加 attempt_count 并写入
  `job.recovered`。
- **审批恢复**：退款不是审批弹窗直接调用工具，而是先进入 `waiting_approval`，
  保存参数和检查点；批准后重新入队，由 Worker 执行。
- **MCP 安全接入**：Bridge 管理持久会话、工具白名单、审批策略、健康检查和
  敏感字段脱敏。
- **评测门禁**：Draft 版本必须同时满足准确率、P95 延迟和平均成本阈值。

推荐句式：

> 这里最关键的设计不是加了一个审批按钮，而是把审批建模成一次持久化状态迁移。
> Web 请求只负责记录决策，真正的写操作仍由可恢复的 Worker 执行。

### 1:35-1:50 质量和结果

> 我用 15 项 API 集成测试覆盖运行、审批、租户隔离、版本发布和 MCP；另外验证了
> stdio 与 Streamable HTTP 两种传输。固定回归集的 8 条用例全部通过，Next.js
> 构建和 GitHub Actions CI 也已通过。

### 1:50-2:00 收束与下一步

> 这个项目验证了 Agent 从定义、工具绑定、持久执行、观测、审批到评测发布的完整
> 生命周期。下一步会接入 OIDC/SSO、持久化幂等表和 pgvector 检索，并把高并发任务
> 分发替换为 Redis Streams 或消息队列。

## 3. 五分钟扩展版本

### 3.1 业务问题

用一句话说明谁会使用：

> `[企业客服团队 / 运营团队 / AI 平台团队]` 需要在 `[订单查询、退款、工单]`
> 流程中使用 Agent，但不能接受任务丢失、越权写操作或不可解释的版本退化。

### 3.2 核心矛盾

不要只说“用了 FastAPI 和 Next.js”，先讲矛盾：

- 响应速度要求 API 快速返回，但 Agent 执行可能很慢。
- 工具能力越强，误操作和安全风险越高。
- Prompt 改动成本低，但线上质量退化代价高。
- 多租户共享基础设施，但数据与权限必须严格隔离。

### 3.3 架构决策

每个决策按“问题 -> 选择 -> 代价”回答：

| 问题 | 当前选择 | 代价与后续 |
|---|---|---|
| HTTP 请求直接执行会丢任务 | 数据库任务队列 + 独立 Worker | 当前轮询有延迟，可替换 Redis Streams |
| 状态与历史混在一起难以审计 | Run 物化状态 + append-only RunEvent | 事件表增长，需要归档和保留策略 |
| 审批弹窗直接执行写工具 | 检查点、等待审批、重新入队 | 状态机更复杂，但可恢复 |
| MCP 直接暴露给 Runtime | Bridge、白名单、超时、会话管理 | 当前仍是受控服务器配置，未来需 OAuth |
| 人工比较 Prompt | 固定回归集 + 发布门禁 | 数据集治理和标注成本更高 |

### 3.4 一次运行的生命周期

```text
queued
  -> running
  -> waiting_approval -> queued -> running -> completed
  -> completed
  -> failed
  -> rejected
  -> needs_input
```

讲解重点：

- `waiting_approval` 是持久化状态，不依赖浏览器页面是否仍打开。
- 审批通过后重新入队，Worker 从检查点恢复。
- 每次执行尝试递增 `attempt_count`，Trace 保留失败和恢复证据。

### 3.5 MCP 工具链

> Bridge 读取受信任的服务端配置，通过官方 MCP SDK 初始化连接。发现工具时保存
> JSON Schema、readOnly/destructive/idempotent 注解和审批策略；调用前检查工具
> 白名单，并复用持久会话。Runtime 在 Trace 中记录工具来源、MCP Server 和
> remote name。

重点区分：

- stdio：Bridge 管理子进程，适合本地或受信工具。
- Streamable HTTP：连接远程服务，适合独立部署的工具服务。

### 3.6 发布门禁

> 新版本先处于 Draft。发布检查在同一数据集上执行 8 个用例，并同时检查最低
> 准确率、最高 P95 延迟和最高平均成本。任意一个失败都不更新 published 版本，
> 同时保存 ReleaseCheck 审计记录。

### 3.7 结果、边界与下一步

结果：

- 15 项 API 集成测试通过。
- stdio 与 Streamable HTTP MCP 测试通过。
- 生产构建和 CI 通过。
- 演示包包含审批恢复、Trace 和发布门禁。

明确边界：

- 当前认证是演示账号密码，生产应接 OIDC/SSO。
- 当前内置工具幂等缓存部分在内存中，生产应使用持久化幂等表。
- 当前评测同步执行，生产应进入独立评测队列。
- 当前检索是词法检索，生产可替换 pgvector 与 reranker。

## 4. 三项故事库

面试官追问时，从中选择一个展开：

### 故事 A：Worker 崩溃恢复

```text
原子领取 -> 写入 lease -> 心跳续租 -> 进程死亡
-> lease 过期 -> 条件更新回 queued -> 新 Worker 领取 -> job.recovered
```

### 故事 B：敏感操作审批

```text
识别退款 -> 查询订单 -> 保存拟调用参数 -> waiting_approval
-> Owner/Approver 批准 -> 重新入队 -> 从检查点恢复 -> 执行退款
```

### 故事 C：版本质量门禁

```text
Draft -> 固定数据集回归 -> 准确率/延迟/成本比较
-> 通过则发布并 supersede 旧版
-> 失败则保留 Draft 和 ReleaseCheck 审计
```

## 5. 演示顺序

时间不足时演示以下四幕：

1. Dashboard：展示平台整体运行、审批和质量视图。
2. Playground：注入工具超时，展示自动恢复。
3. 审批页：展示暂停、审批和 Trace 恢复。
4. 评测中心：展示 8/8 通过和发布门禁。

不要在演示时逐页解释所有按钮。每页只回答一个问题：

- Dashboard：平台解决了什么？
- Trace：执行过程是否可信？
- Approval：高风险动作如何被控制？
- Evaluation：新版本为什么可以上线？

## 6. 常见追问的过渡句

- 被问技术栈时：

  > 技术栈不是设计起点。我先按持久执行、权限边界、可观测性和发布安全拆问题，
  > 再选择 FastAPI、Next.js、SQLAlchemy 和 MCP SDK。

- 被问为什么不用纯前端流程时：

  > 浏览器关闭后任务仍需继续，敏感操作也不能由前端直接确认，因此审批和恢复必须
  > 落在服务端状态机里。

- 被问是否生产可用时：

  > 当前是可完整演示的 MVP。核心闭环是可验证的，但生产化还需要 OIDC、持久幂等、
  > 数据库迁移、限流、隔离执行和更完整的评测治理。

## 7. 个人化检查清单

- 用一句话说清“谁在什么流程中使用它”。
- 至少准备一个真实设计取舍，而不只是功能列表。
- 至少说出一个代码位置或关键状态迁移。
- 数字只使用能够复测的结果。
- 主动说明当前边界，避免把 Demo 描述成生产系统。
- 结尾给出下一步，而不是停在“功能做完了”。
